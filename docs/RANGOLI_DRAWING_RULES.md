# Rangoli Drawing Contract — Mandatory for All Artwork

**Status: normative.** This file, root `AGENTS.md`, the executable `drawing-contract.js`, and CI are authoritative. Never change only documentation or only the animation code.

## Mandatory five-stage sequence

Every `vector_draw` and successfully processed `image_auto_trace` design MUST complete these non-overlapping stages, in this exact order:

1. **dots** — Place guide dots/anchors one by one. Use actual design dots when authored; otherwise use anchors computed from traced geometry. Never invent an unrelated decorative dot grid.
2. **outline** — Draw paths with a moving powder tip, one stroke after another, following their ordered geometry. Strokes may join dots, loop around them, or use freehand anchors depending on the design.
3. **outline_complete** — Render the entire finished outline, with a nonzero hold interval. **No colour or fill is allowed in this stage.**
4. **fill** — Reveal **one bounded colour region at a time** inside the traced fill masks or authored polygons. The full bitmap must never be displayed by a wedge, radial full-picture wipe, or paint-bucket effect masquerading as real drawing.
5. **final** — Only after filling is complete, show remaining fine detailing and the finished frame. Sparklers/highlights may finish here but must never hide a missing outline/fill phase.

The playable timeline is generated by `RangoliDrawingRules.timeline` in `drawing-contract.js`, which ensures strict ordering with positive durations and explicit checkpoints. The renderer must gate fills at the **start of stage 4**, not at the moment outline drawing ends.

## Input classes and truthful claims

| Mode | Source | Drawing behavior | Can claim tutorial accuracy? |
|---|---|---|---|
| `vector_draw` | Authored points, paths and regions | Mandatory 5 stages | **Only after human review, with verified dot/path/fill correspondence** |
| `image_auto_trace` | User-uploaded PNG/JPG/WebP/SVG/AVIF or gallery image | Estimated anchors, traced contour paths, connected colour components, then mandatory 5 stages | **No.** Estimated only; `tutorialCapable=false`, `verification=automatic_unreviewed` |
| `image_preview` | Unprocessed or untraceable image thumbnail | Static asset preview; no pretend drawing | **No.** Never advertise as Draw Mode |

**Special case:** Not every rangoli is based on an evenly spaced dot grid. Use accurately placed *guide anchors* for floral, diya, peacock and other freehand designs, and label them as such. Do not assert that these are original pulli dots unless verified.

## Image processing requirements

- All image ingress routes MUST call `RangoliImageProcessor.process`, including gallery selection, file upload, drag/drop, and background-removal reprocessing.
- Extraction must yield geometrically meaningful dots, a nonempty ordered contour set, and bounded colour regions. **At least 80% of guide dots must align within 28 Canvas units of a point on an actual outline stroke.** Arbitrary decorative dot grids are invalid. Every auto-generated region must be revealed separately.
- Browser-only extraction is intentionally approximate: it groups similar-colour connected pixels, traces region boundaries, and derives dots from contour starts/turns. Automatic order is NOT the artist's instruction sequence.
- After processing, use `buildProcessedImage` and the common `libraryVectorFrame` renderer. Never call `wedgeImage` or replace it with another bitmap reveal.
- If geometry cannot be extracted safely (invalid image, insufficient detail, decoding/taint failure), **fail closed**: retain the original gallery thumbnail and report that no reliable drawing was created. Never fall back to a fake tutorial.
- The static gallery metadata may classify an image `image_preview`; selecting it attempts automatic tracing and runs it as `image_auto_trace` only upon success.
- Rendered output, controls, filenames, badges, docs and exports must not call an unverified auto-trace a real tutorial.

## Definition of done — acceptance gates

- Five visible stages match the shared timeline; the **outline_complete** interval is actually observable.
- At the end of **dots**, no lines or fills exist.
- During **outline**, no fill pixels are displayed.
- During **outline_complete**, all strokes exist; no colour fill has begun.
- During **fill**, outlined geometry persists while each clipped colour region appears progressively.
- During **final**, colour work is complete and details can finish.
- All six existing `vector_draw` models validate.
- A synthetic raster fixture auto-traces into nonzero dots, strokes and regions and has `tutorialCapable=false`.
- Invalid and blank image inputs fail closed.
- Search, filtering, theme changes, backgrounds, speed adjustment, fullscreen and PNG/WebM export remain usable.
- GitHub Actions runs the contract test and builds a complete `digiops-release` artifact containing the shared contract, image tracer and drawable datasets.

## How to add a new design

1. Identify rights/provenance and whether it is dot-grid, anchor-guided freehand, or preview-only.
2. If authored, define actual dots, ordered strokes and bounded fills in `drawable-designs.js`, and validate the model.
3. If imported from an image, let the image processor derive *estimated* anchors, paths and fills; do not promote its mode to `vector_draw` without reviewed source geometry.
4. Test the 5 stages by scrubbing and by playback at slow and fast outline speeds.
5. Add/adjust automated tests; never weaken the contract to pass a broken design.
6. Update README/gallery metadata without claiming authenticity that cannot be substantiated.

For real-world tutorial accuracy, future work needs an editor for manually correcting dot positions, topology, stroke ordering, fill boundaries and powder motion; **automatic segmentation alone cannot supply that proof**.
